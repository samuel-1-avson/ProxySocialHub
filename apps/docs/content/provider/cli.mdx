Providers sell bandwidth by running the **provider-node** tunnel daemon against **`proxy.proxyhubb.com:3128`**. The companion CLI binary is **`proxyhubb-cli`**.

Do **not** confuse provider tunnel **`:3128`** with buyer CONNECT **`:8090`**.

## Recommended path

The simplest way to connect a computer is to **pair** it — no token to copy, no script to run:

1. Download `provider-node` from [CLI Tools](https://proxyhubb.com/dashboard/provider/cli)
2. Run `provider-node pair` and approve the code it shows in your dashboard ([details](#pair-this-computer))
3. Run `provider-node start`

Already set up through the wizard? Then skip pairing:

1. Complete the in-app [provider setup wizard](https://proxyhubb.com/dashboard/provider/setup)
2. Download CLI + `provider.toml` from [CLI Tools](https://proxyhubb.com/dashboard/provider/cli)
3. Start the node — **do not run `join` / register again** after the wizard (reuse the downloaded config / `--node-id`)

### Pair this computer

```bash
provider-node pair
```

The command prints a link and a short code such as `BCDF-GHJK` and opens the link in your browser. Sign in if asked, check that the **device name and system** shown match this computer and that the code matches, then choose **Approve this computer**. The command finishes on its own, writes `provider.toml`, and tells you to run `provider-node start`.

- The code works **once** and expires after **10 minutes**. If it lapses, run `pair` again.
- Approving creates a node for the device and a provider token named `Paired: <device name>`. The token **does not expire**, so an unattended node never drops offline because a key lapsed. Revoke it any time under [Tokens](https://proxyhubb.com/dashboard/provider/tokens) and the device is cut off.
- Only approve a code **you** just started on a computer **you** own. A code someone else gives you would connect their computer to your account.
- `pair` refuses to run if a `provider.toml` already exists (so you never approve something that then fails to save). Use `--force` to replace it, or `--config <path>` to write elsewhere.
- Flags: `--api-url`, `--gateway-addr`, `--device-name <name>` (defaults to the computer's name), `--no-browser` (print the link instead of opening it).

## Downloads

Binaries ship via GitHub Releases and:

```http
GET /v1/cli/download?platform=…&arch=…&version=…&package_type=…
```

The dashboard detects OS/arch and offers the matching asset. Packages are **not** published to crates.io for day-to-day installs.

### npm / pip (same binaries)

Sellers and providers can also install a thin wrapper that downloads `provider-cli` / `provider-node` from the API and proxies commands:

```bash
# Easiest (Windows / macOS / Linux) — Dashboard → My nodes → Connect → Setup this PC
# Downloads a one-click setup script that writes config, installs the CLI, and starts the node.

# npm
npm install -g @proxyhubb/provider@latest
proxyhubb-provider install
proxyhubb-provider --daemon doctor

# PyPI
pip install -U proxyhubb-provider
proxyhubb-provider install
proxyhubb-provider --daemon doctor

# Cargo (from source — not crates.io)
cargo install --locked --git https://github.com/samuel-1-avson/ProxySocialHub.git --tag provider-v1.0.6 --path services/provider-node
```

Env overrides: `PROXYHUBB_API_URL`, `PROXYHUBB_CLI_VERSION`. Use `proxyhubb-provider install` to force re-download of the current latest binary, `proxyhubb-provider path` to print the cached binary, and `--daemon` to target `provider-node` instead of `provider-cli`.

If you downloaded `provider.toml` yourself, install it with `provider-node config install --from <path-to-file>`. The command prints where the file sends traffic (control API, gateway, TLS settings) and asks for confirmation before writing it to the config path (`%APPDATA%\proxyhubb\provider.toml` on Windows). `provider-node` no longer imports files from your Downloads folder automatically.

There is **no separate “seller CLI”** — marketplace sellers are providers; automate listings via the [SDKs](/docs/sdks) and run bandwidth with this CLI / node.

## CLI commands

| Command | Purpose |
|---------|---------|
| `pair` | Connect this computer by approving a short code in the dashboard; write `provider.toml` |
| `join` | Enroll with provider token; write `provider.toml` |
| `start` | Start the tunnel daemon |
| `stop` | Stop |
| `status` | Local status |
| `doctor` | Config / connectivity checks |
| `dashboard` | Open provider dashboard helpers |
| `watch` | Follow logs / health |
| `install` | Service install helpers |
| `paths` | Show config/data paths |

### Join (fresh enroll)

```bash
proxyhubb-cli join \
  --api-url https://api.proxyhubb.com \
  --key <provider_token> \
  --gateway proxy.proxyhubb.com:3128

# Reuse a dashboard-created node (skip re-register):
proxyhubb-cli join … --node-id <uuid>
```

### Start / doctor

```bash
proxyhubb-cli doctor --config provider.toml
proxyhubb-cli start --config provider.toml

# Or run the daemon binary directly:
./provider-node --config provider.toml
```

Confirm the node goes **online** under [My nodes](https://proxyhubb.com/dashboard/provider/nodes). Browser “ping” is not a real tunnel — use Connect + CLI start.

### Start automatically at sign-in

```bash
provider-node service install      # turn on
provider-node service start        # start now, without signing out
provider-node service status
provider-node service uninstall    # turn off
```

| OS | What `service install` creates |
|----|-------------------------------|
| Windows | A per-user startup entry (no administrator rights). It appears under **Task Manager → Startup apps** as “ProxyHubb Provider Node”, where you can also switch it off. |
| macOS | A LaunchAgent in `~/Library/LaunchAgents` |
| Linux | A systemd **user** unit |

On Windows the entry runs `provider-node start --background`, which launches the tunnel as a hidden background process and exits (a console window may flash for a moment at sign-in). It starts when you sign in, not at boot, so a Windows machine nobody signs in to needs a different setup. Earlier builds registered an `sc.exe` service named `proxyhubb-provider` that could never start; `service uninstall` removes it if it has permission, otherwise run `sc.exe delete proxyhubb-provider` from an administrator prompt.

## Config (`provider.toml`)

Typical fields (written by `join` / validated by provider-node):

| Field | Notes |
|-------|--------|
| `control_api_url` | e.g. `https://api.proxyhubb.com` |
| `gateway_addr` / `gateway_addrs` | Tunnel endpoint (`host:3128`) |
| `jwt_token` / `api_key` | Auth material from join |
| `node_id` | Registered node UUID |
| `provider_signing_key` | Usage proof signing — keep secret |
| `connection_type` | `residential` \| `mobile` \| `datacenter` \| `fiber` |
| `use_tls` | TLS to gateway when required |
| `metrics_port` | Default `9090` |
| `max_connections`, `bandwidth_limit_mbps` | Capacity caps |

Keep `provider.toml` private. Never commit signing keys.

## Proof signing

If the dashboard shows unsigned usage / “Fix proof”, ensure `provider_signing_key` matches the key bound at registration. CLI `join`/`register` generates it; web-only flows may need the fix banner path.

## Common errors

| Symptom | Fix |
|---------|-----|
| Node stays offline | Run `doctor`; check `:3128` reachability and token |
| Accidental second node | Use wizard config / `--node-id`; don’t re-`join` blindly |
| Unsigned usage | Align `provider_signing_key` with registered key |
| Connected to wrong port | Providers use **3128**, buyers use **8090** |
