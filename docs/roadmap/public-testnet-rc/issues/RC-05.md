# RC-05 Fix Browser Token And Websocket Auth Handling

Suggested assignee: `samuel-1-avson`
Owner role: Frontend Lead
Supporting roles: Security Lead, QA/Release Lead
Initial status: Done
Depends on: RC-04
Target window: Days 5-6

## Summary

Replace long-lived query-string websocket auth and reduce browser token exposure relative to the current localStorage-based model.

## Acceptance Criteria

- Websocket auth no longer relies on long-lived JWTs in the query string.
- Browser token storage has lower exposure than the current `localStorage` pattern.
- Login, refresh, logout, and protected-route access pass E2E coverage.

## Notes

- Browser auth storage now migrates legacy tokens out of `localStorage`, keeps access tokens in `sessionStorage` plus cookie sync, and no longer persists refresh tokens in `localStorage`.
- Websocket and SSE paths now rely on cookie-backed auth instead of `?token=` query parameters.
- Focused validation passed with `npm run typecheck`, `go test ./internal/middleware`, and `go test ./internal/api -run '^$'`.
- The focused Chromium auth spec now passes locally against `http://localhost:4011` and `http://localhost:18080`.
- The earlier empty responses on `/login`, `/register`, and `/dashboard` were environmental, not app regressions: Docker/IPFS (`creg-ipfs`) already owns host port `4001` on this machine.
- Local defaults were updated so the web dev server and Playwright now use `4011`, which matches the passing local auth validation path without requiring a manual `TEST_BASE_URL` override.
