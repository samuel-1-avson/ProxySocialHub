# RC-04 Separate Gateway Auth And Session Signing Secrets

Suggested assignee: `samuel-1-avson`
Owner role: Security Lead
Supporting roles: Backend Lead, DevOps/SRE Lead
Initial status: Done
Depends on: RC-01
Target window: Days 3-4

## Summary

Separate gateway route authentication from session-intent signing so a single secret leak cannot compromise both surfaces.

## Acceptance Criteria

- Session-intent signing no longer depends on the same secret used for gateway route auth, or a documented exception with compensating controls is approved.
- Secret names, env examples, and deployment docs are updated.
- Rotation steps are validated in a non-production environment.

## Notes

- This issue is assigned to the same DRI as the protocol and backend work, so it should stay tightly scoped to secret-boundary separation for this sprint.
- Session-intent signing now uses `SESSION_SECRET`; gateway control-plane auth remains on `GATEWAY_SHARED_SECRET`.
- Compose and env examples were updated so edge-gateway receives both secrets explicitly.
- A dedicated rotation runbook now exists at `docs/runbooks/gateway-session-secret-rotation.md` and passed markdown validation.
- The gateway secret rehearsal is now proven live: the old `X-Gateway-Auth` header returns `401`, while the rotated header reaches the route and fails later with `404` on a fake intent ID.
- `SESSION_SECRET` has been rotated in local non-production compose and both `control-api` and `edge-gateway` returned healthy after restart.
- The `edge-gateway` image was rebuilt from source and redeployed successfully after switching the local build to Docker's `default` builder and tightening the Dockerfile fetch cache layer.
- Live session-intent acceptance is now proven on the rebuilt image with an array-`aud` JWT claim: a token signed with the pre-rotation `SESSION_SECRET` returns `407 Proxy Authentication Required`, while the rotated secret authenticates successfully and reaches provider selection.
- The rotated-secret CONNECT probe now fails later with `503` because the local provider registry has no healthy nodes available, and the gateway logs show `Authenticated session: intent:intent-new-proof` instead of `InvalidSignature`.
- `http://localhost:18090/health` remained `200` after the proof, so the remaining `503` is downstream capacity/registry state, not a secret-boundary auth regression.
